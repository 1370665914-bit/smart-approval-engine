# 智能审批引擎链路与迁移手册

- **版本**：v1.0（开源脱敏版）
- **整理时间**：2026-08-19
- **适用范围**：主 Agent 及其财务审批辅助链路
- **文档性质**：架构盘点、运行链路、迁移基线
- **安全口径**：本文已脱敏，不包含 App Secret、Access Token、个人收件人 ID、OA 凭据、Cookie、合同正文、发票原文或银行账号。公司专有标识一律以 `<占位>` 表示。

## 1. 一页总览

当前审批系统由三层组成：

1. **Agent 层**：接收消息、按飞书账号路由、调度专业 Agent。
2. **本地审批业务层（approval_center）**：连接 OA，抓取结构化字段和附件事实，运行确定性规则、生产门禁、状态同步和通知。
3. **输出层**：向飞书发送只读建议卡片；OA 动作和台账写入默认关闭。

核心原则：模型负责编排和解释，确定性规则负责业务判断，生产门禁负责最后的发送安全，人工负责最终审批动作。

## 2. 当前 Agent 拓扑

```text
飞书（主账号）
        │
        ▼
主 Agent
        │ 负责总协调、任务拆解、调用子 Agent
        ├── OCR Agent        文档/OCR
        ├── 合规 Agent       合规/合同
        ├── 校对 Agent       校对/匹配
        └── approval Agent   审批消息入口与审批中台适配
```

### 2.1 路由事实

路由由 Agent 框架配置中的 `bindings` 决定（以下为示例路由配置）：

| 飞书账号 | 目标 Agent | 用途 |
|---|---|---|
| `default` | 主 Agent | 主对话与总协调 |
| `ocr` | OCR Agent | OCR/文档处理 |
| `contract` | 合规 Agent | 合同合规 |
| `matcher` | 校对 Agent | 校对与匹配 |

模型并不替代本地确定性规则。

## 3. 两条审批入口

### 3.1 飞书消息入口

适用于用户在飞书直接发送审批、报销、付款、合同、发票或 OA 审核材料。

```text
飞书消息
  → 路由到审批子 Agent
  → 解析原文、申请人、部门、金额、币种、附件、OA URL
  → 调用本地审批业务层的飞书入口适配器
  → 业务层落地为 ApprovalRequest
  → 规则/审核/归档链路
  → 返回短状态或只读建议
```

入口适配器负责把不稳定的飞书 payload 归一化为内部对象。支持从消息文本兜底推断标题、金额和审批编号，但推断值必须在后续证据链中标记为 inferred，不能冒充权威字段。

审批子 Agent 的边界：

- 不自行做最终审批决定。
- 不直接写外部台账。
- 不执行 OA 通过、驳回、提交、保存或转发。
- 业务判断、台账和后续执行由本地审批业务层所有。

### 3.2 OA 实时待办入口

适用于 OA 中出现新的合同付款或采购合同待办。

```text
OA REST API
  → 定时扫描（如每 30 秒）
  → 仅保留目标流程
  → 读取可读字段与流程元数据
  → 本地导出并解析附件（PDF 解析 + macOS Vision OCR）
  → 规则门控确定性规则预判（当前 shadow 模式）
  → 审批子 Agent 做只读建议编排
  → 最终发送门禁
  → 飞书 notifier 发送一张 Card 2.0
  → 卡片状态库记录幂等、发送和状态同步
  → OA 状态变化后 reconcile 更新卡片状态
```

当前实时 watcher 已从旧的浏览器自动化路径迁移到 OA REST API + Agent 子任务。旧的浏览器自动化方案已废弃，不应恢复或作为迁移依赖。

## 4. 实时审批详细链路

### 4.1 扫描与范围控制

- 生产进程：`python -m approval_center.realtime.oa_status_watcher --loop`
- launchd 标签示例：`com.<公司域名>.approval-center.oa-status-sync`
- 扫描间隔：30 秒
- API 失败：按配置重试，使用线性退避
- 业务范围：`contract_payment`、`purchase_contract`
- 单项分析只处理指定 `request_id`，不扫描其他流程。

### 4.2 OA 数据获取

优先使用 OA REST API：

- 待办列表：`api_scanner.scan_pending`
- 流程详情：`client.request_detail(request_id)`
- 可读字段：`readable_fields(client, request_id)`
- 流程日志：`client.request_log(request_id)`（需要节点历史时使用）

关键字段包括流程号、申请人、部门、付款方式、付款金额、付款主体、收款单位、收款账户、付款事由和关联采购申请。内部 ID 字段必须通过 `fieldShowValue` 转换为人类可读值。

### 4.3 附件事实链

附件只在本机处理，不上传外部服务：

```text
OA 附件引用
  → 本地导出
  → PDF 文本层提取
  → 无文本层时 macOS Vision OCR
  → document_facts / invoice_info
  → 每个事实保留来源、页码、解析器、置信度
```

事实状态：

- `confirmed`：权威来源直接可见
- `normalized`：不改变含义的标准化，例如人民币 → CNY
- `inferred`：由上下文推断
- `unknown`：不可用或不可读

合同正文、发票图像或附件内容缺失时，相关规则必须保持 `pending`，不能用表单字段猜测替代附件证据。

### 4.4 确定性规则与规则门控

规则目录示例：`<project_root>/approval_center/rules/`

主要模块：

- `engines/rule_loader.py`：加载 YAML 规则
- `engines/decision_engine.py`：通用决策
- `engines/structured_checklist.py`：结构化检查项
- `engines/evidence_facts.py`：证据事实
- `risk_features/evaluator.py`：风险特征
- `realtime/rules_gate.py`：实时规则前置门控

当前配置（示例）：

```yaml
realtime_advisory:
  rules_gate:
    mode: shadow
    parse_attachments: true
    max_auto_skip_amount: 50000   # 示例阈值，按公司制度配置
    allow_flow_types: [contract_payment]
```

`shadow` 只记录规则本来会如何判断，不改变正式行为，也不跳过模型。只有未来满足真实样本、错误率、差异复核和连续稳定性条件后，才考虑切换 `enforce`。

规则门控的安全约束：

- 只有低风险、明确通过且检查项完整，才具备跳过模型的理论资格。
- 超过配置阈值的单据不得由规则门控直接放行。
- 非白名单流程不得跳过模型。
- `pending`、证据不足、解析失败或系统异常不能被升级为通过。

### 4.5 模型编排边界

watcher 通过 Agent 框架 CLI 启动审批子 Agent，传入唯一 `request_id` 和流程分类。

模型任务是：

- 遵循审批建议 skill
- 先做 preflight
- 读取 OA 结构化字段和本地附件事实摘要
- 解释规则结果、证据缺口和人工复核建议
- 通过正式 notifier 发送一张 Card 2.0

模型禁止：

- 点击 OA 通过、驳回、提交、保存、转发
- 填写 OA 审批意见
- 写外部审批台账
- 上传合同、发票、附件全文或截图到外部服务
- 把 pending/fail 改写成 pass

### 4.6 最终发送门禁

所有正式审核卡片必须经过 `realtime/production_gate.py`：

1. 附件发现、下载、解析数量闭环一致。
2. 无附件系统错误、下载错误或解析异常。
3. required checks 存在且均为 `pass` 或 `fail`。
4. 不存在 `pending`、`missing`、`low_confidence`、`system_error` 等未完成状态。
5. 决策稳定、当前申请仍在 OA 待办中。
6. 熔断器未触发。
7. 幂等预占成功。

证据不足时走独立的人工复核卡门禁；系统错误仍 fail-closed，不发送普通结论卡。

### 4.7 飞书通知与状态同步

通知入口：`approval_center.notifiers.feishu_notifier.notify_scan_result`

通知约束：

- 一单一张 Card 2.0
- 结论、风险、金额/币种、申请人、付款方/收款方
- 通过项和未决项分开
- 附件解析状态和人工复核原因清晰可见
- 最多一个打开 OA 的跳转按钮
- 不提供通过、驳回、提交、保存、转发回调按钮

`card_state_store` 记录发送幂等键、message_id、审批编号与状态。OA 待办消失后，通过流程日志或状态接口做 reconcile，并更新卡片状态。

## 5. 普通报销工作台链路

审批中心还保留一条产品化的本地工作台链路，和 OA 实时合同付款链路并行：

```text
任意输入源
  → ExpenseCase
  → FormAgent 生成填单草稿
  → AuditAgent 规则审核与解释
  → 人工复核
  → ArchiveAgent 生成归档包/PDF
  → ProductStore 本地 JSONL
  → 外部台账摘要同步（当前写入关闭）
```

核心数据文件：

- `data/expense_cases.jsonl`
- `data/audit_results.jsonl`
- `data/archive_records.jsonl`

台账在新架构中是输出连接器，不是核心数据库；后续可迁移到 SQLite/Postgres。

## 6. 安全开关与信任策略

当前关键开关均为保守状态：

| 开关 | 当前状态 | 影响 |
|---|---:|---|
| `approval.auto_execute_enabled` | `false` | 不自动执行审批动作 |
| `approval.card_actions_enabled` | `false` | 不启用卡片回调动作 |
| `approval.card_actions_dry_run` | `true` | 即使触发动作也只演练 |
| `oa.allow_click_enabled` | `false` | 不允许点击 OA 控件 |
| `ledger.write_enabled` | `false` | 不写外部台账 |
| `agent_governance.trust_level` | `assist` | AI 只给建议，人工确认 |
| `rules_gate.mode` | `shadow` | 只观测，不改变正式行为 |

信任等级 `assist` 下，任何建议通过都不能自动执行；中高风险、证据不足、规则冲突和金额超限必须人工处理。

## 7. 迁移清单

### 7.1 必须迁移的代码与配置模板

- `approval_center/` 源码
- `rules/` YAML 规则
- `templates/` 工作台与队列页面
- `requirements.txt` / Python 虚拟环境依赖清单
- `config/settings.example.yaml`
- `scripts/mac/` 启动、健康检查和 launchd 模板
- `docs/` 架构、事故复盘和迁移资料

### 7.2 需要重新配置的本机资源

- Python 3.11+ 与项目虚拟环境
- Node.js 20+
- Google Chrome
- Chrome CDP 端口 `9222`
- OA 登录态
- OA API 环境变量文件（示例：`config/oa_api.env`，不含真实凭据）
- Agent 框架主 Agent/子 Agent 配置
- 飞书 bot/app 权限与 notifier 配置
- 本机 launchd 服务

### 7.3 不应直接复制

- Chrome CDP profile 与浏览器 Cookie
- OA 登录态
- 飞书登录态或 CLI 私有配置
- `config/settings.yaml` 中的真实凭据
- 大量运行日志、临时文件、`__pycache__`
- 生产 SQLite 状态库，除非明确需要保留幂等和历史状态

迁移原则：复制模板，重新注入本机凭据；不要复制认证状态。

## 8. 推荐迁移顺序

1. 固定代码版本并导出不含秘密的迁移清单。
2. 在目标机器上安装 Python、Node、Chrome 和 Agent 框架依赖。
3. 部署 `approval_center` 源码与规则。
4. 根据目标机器创建 `settings.<环境>.yaml`，只写本机路径和开关。
5. 配置 OA API 环境变量；不把凭据写进 Git 或文档。
6. 登录 OA，确认 CDP 端口可用；确认 REST API preflight 为安全。
7. 配置主 Agent、审批子 Agent 和相关路由。
8. 先启动工作台并检查健康端点。
9. 手动执行一次只读扫描，验证字段读取、附件解析和规则结果。
10. 验证 notifier 走正式发送门禁，且不产生 OA 动作或台账写入。
11. 观察健康、性能、shadow 差异和 watcher 日志。
12. 连续稳定后再启用 launchd；保持自动执行开关关闭。
13. 新旧机器并行观察，确认无重复卡片后再切换定时任务。

## 9. 迁移验收标准

### 功能

- [ ] 飞书主账号能进入主 Agent。
- [ ] 审批消息能路由到审批子 Agent。
- [ ] OA REST API preflight 成功。
- [ ] 只扫描白名单流程。
- [ ] 可读字段接口能返回可读字段。
- [ ] PDF 文本提取与 OCR 均能工作。
- [ ] 规则结果包含逐项状态和证据来源。
- [ ] 正式卡片一单一张，且通过 notifier 发送。
- [ ] OA 状态变化能被 reconcile。

### 安全

- [ ] OA 点击开关为 false。
- [ ] 卡片动作开关为 false，dry-run 为 true。
- [ ] 台账写入开关为 false。
- [ ] 当前信任等级为 assist。
- [ ] 普通卡发送经过最终正式门禁。
- [ ] pending、解析失败、系统错误不会发送普通结论卡。
- [ ] 附件正文不离开本机。
- [ ] 日志未包含 token、Cookie、完整账号、附件正文或个人收件人信息。

### 稳定性

- [ ] watcher 单实例运行。
- [ ] launchd 重启策略生效。
- [ ] 失败重试与超时 watchdog 生效。
- [ ] 状态库可读，幂等键不会重复发送。
- [ ] 熔断器指标达到阈值时会停止普通卡发送。
- [ ] 迁移前后规则回归测试通过。

## 10. 观测与排障入口

优先检查：

- `logs/realtime_health.json`：健康状态
- `logs/realtime_perf.jsonl`：阶段耗时
- `logs/oa_status_watcher.log`：watcher 主日志
- `logs/realtime_analysis_<request_id>.log`：单项 Agent 分析日志
- `logs/rules_shadow_diff.jsonl`：规则门控 shadow 差异
- `logs/attachment_parse.jsonl`：附件解析记录
- `logs/delivery_breaker.json`：发送熔断状态
- `logs/approval_card_state.sqlite3`：卡片与幂等状态

排障优先级：

1. preflight / OA API 健康
2. 附件发现、下载、解析闭环
3. required checks 与证据置信度
4. production gate 分类
5. notifier 返回
6. card state 幂等与状态同步

## 11. 当前已知风险与迁移注意事项

1. `settings.yaml` 仍包含不应进入文档或版本库的真实配置项，迁移必须使用本机覆盖文件并重新审计秘密。
2. 旧文档存在历史状态；迁移时以本手册、当前源码和运行进程为准。
3. OCR 证据不能自动等同于高置信度结构化证据；低置信度必须人工复核。
4. REST API 不一定能读取附件正文，附件链路失败时必须 fail-closed。
5. `rules_gate` 当前为 shadow，不能把 shadow 日志理解成已启用自动放行。
6. 台账写入默认关闭；任何启用都必须单独评估权限、字段映射、幂等和回滚。
7. OA 自动执行仍关闭；迁移目标是恢复只读建议链路，不是扩大自动化权限。

## 13. 结论

迁移时真正需要恢复的是一条"只读、证据驱动、人工兜底"的审批建议链路：

```text
Agent 路由
  → 审批子 Agent / 主 Agent 调度
  → 审批业务层输入适配
  → OA REST + 本地附件事实
  → 确定性规则
  → 解释性 Agent
  → production gate
  → 飞书只读卡片
  → 状态同步与审计日志
```

任何自动执行、卡片回调、台账写入和规则 enforce 都不是本次迁移的默认目标，必须作为独立变更单独确认。
