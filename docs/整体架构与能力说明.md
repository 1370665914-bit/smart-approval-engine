# 智能审批引擎整体架构与能力说明

> 面向内部知识沉淀、架构查看与对外展示汇报

- **版本**：v2.0（开源脱敏版）
- **更新时间**：2026-08-19
- **系统定位**：面向财务付款与采购合同场景的智能审核辅助平台
- **运行原则**：证据驱动、规则优先、模型增强、人工决策、安全闭环

## 1. 系统简介

智能审批引擎以企业 OA 审批流程为入口，将结构化表单、合同、发票及业务附件转化为可追溯的审核事实，结合确定性规则与智能分析能力，对每笔申请输出逐项核验结果、风险判断和处理建议，并通过飞书卡片交付给审核人员。

系统当前重点覆盖：

- 合同付款申请
- 采购合同审批
- 发票与付款信息一致性核验
- 合同、验收、账单等附件事实抽取
- 费用期间、主体、金额、币种等交叉校验
- 证据不足、材料缺失和系统异常的分级处置

系统不替代最终审批人。当前定位是"智能审核助手"，负责提高信息获取、交叉核验和风险识别效率，最终审批动作仍由人完成。

## 2. 建设目标与业务价值

### 2.1 建设目标

1. 将人工逐页查看表单和附件的工作转化为自动化事实提取。
2. 将分散的审核经验沉淀为可维护、可测试的规则资产。
3. 对关键字段进行跨来源一致性校验，减少遗漏和机械错误。
4. 对每一项结论保留证据来源，提升审核可解释性与可追溯性。
5. 在不扩大审批权限的前提下，为审核人员提供实时、清晰的决策辅助。

### 2.2 业务价值

| 价值方向 | 具体体现 |
|---|---|
| 审核提效 | 自动提取申请人、金额、付款主体、收款方、费用期间、发票等核心信息 |
| 风险识别 | 自动发现主体不一致、金额不一致、期间错配、附件缺失和低置信度证据 |
| 标准统一 | 以 YAML 规则和结构化检查项统一审核口径 |
| 过程可溯 | 每项检查保留来源、页码、解析器、置信度与状态 |
| 安全可控 | 只读运行、人工终审、发送门禁、熔断和幂等机制共同约束 |
| 持续演进 | 规则、解析器、流程类型和输出模板均可独立扩展 |

### 3.1 Agent 协作体系

主 Agent 负责接收需求、识别任务类型和协调专业能力；专业 Agent 按职责完成文档识别、合同合规、信息匹配和审批结果结构化。

| 角色 | 主要职责 |
|---|---|
| 主 Agent | 任务理解、流程协调、结果整合与用户交互 |
| OCR Agent | PDF、扫描件和图片文字识别 |
| 合规 Agent | 合同条款、主体、期限和业务合规核验 |
| 校对 Agent | 表单、合同、发票和收款信息之间的交叉匹配 |
| Approval Agent | 审批数据结构化、调用本地审核引擎、生成审核建议 |

各 Agent 负责不同专业环节，但业务结论必须遵守同一套确定性规则、证据标准和安全门禁。

## 4. 端到端审核链路

```text
OA 新待办或飞书审批材料
  → 识别流程类型与唯一审批编号
  → 获取 OA 结构化字段和流程元数据
  → 发现、下载并解析本地附件
  → 形成带来源与置信度的标准事实
  → 执行逐项确定性审核规则
  → 计算风险等级与未决问题
  → 模型生成面向人的解释和处理建议
  → 最终生产门禁复核完整性与状态
  → 飞书发送单笔审核卡片
  → 持续同步 OA 后续处理状态
```

### 4.1 数据采集

系统通过 OA REST API 获取待办、流程详情、可读表单字段和流程日志。扫描范围限定为已支持的业务流程，单笔分析以唯一 `request_id` 为边界，避免跨流程读取和错误关联。

### 4.2 文档理解

附件在本机完成处理：

- 原生 PDF 优先读取文本层
- 扫描件和图片使用 macOS Vision OCR
- 电子发票使用确定性解析器提取购销方、税号、金额、税率、税额等字段
- 合同、账单、验收文件提取主体、期间、币种和关键日期
- 混合 PDF 支持逐页文本与 OCR 互补

附件内容不上传外部服务，业务材料保留在本地处理边界内。

### 4.3 标准事实与证据

系统不会直接用原始文本作结论，而是先形成标准事实对象。每个重要事实记录：

- 字段名称与标准化值
- 来源文件与页码
- 提取方式或解析器
- 最小必要证据片段
- 置信度等级

置信度分为：

- `confirmed`：权威来源直接确认
- `normalized`：仅做不改变含义的标准化
- `inferred`：根据上下文推断
- `unknown`：缺失、不可读或无法确认

严格一致性规则原则上只接受 `confirmed` 和规则允许的 `normalized` 事实。

### 4.4 规则审核

系统将审核经验沉淀为结构化规则，按流程类型加载对应检查清单。当前主要核验维度包括：

- 付款方式与发票时点
- OA 付款主体与合同主体、发票购买方的一致性
- 收款单位、合同相对方、发票销售方和账户户名的一致性
- 申请金额、发票金额、合同金额和付款节点的一致性
- 费用期间与合同、账单、验收期间的一致性
- 币种在 OA、合同和发票之间的一致性
- 关联采购流程、验收材料和必要附件的完整性
- 重复发票、重复付款及异常表述等风险信号

每项检查输出 `pass`、`fail`、`pending` 或 `not_applicable`，并附带证据和原因。

### 4.5 智能解释

模型用于理解异常上下文、组织审核摘要和生成便于人工阅读的建议，但不能覆盖确定性规则：

- 不得把 `pending` 或 `fail` 改写为 `pass`
- 不得以推断替代缺失证据
- 不得脱离审核结果自行给出审批动作
- 不得将合同、发票或附件内容上传外部服务

系统输出建议包括：建议通过、建议补材料、建议驳回、建议人工复核。

### 4.6 结果交付

每笔申请独立生成一张飞书审核卡片，集中展示：

- 审核建议与风险等级
- 申请人、金额、币种和业务主体
- 已通过检查项
- 失败或未决检查项
- 附件处理状态与人工复核原因
- 打开原 OA 单据的入口

卡片不包含通过、驳回、提交或保存按钮，避免消息侧直接改变 OA 状态。

## 6. 安全治理体系

安全设计不是附加功能，而是审核链路的一部分。

### 6.1 权限边界

当前系统处于辅助审核模式：

- 不自动批准或驳回 OA
- 不自动填写审批意见
- 不启用飞书卡片审批回调
- 不写正式审批台账
- 不扩大模型或 Agent 的执行权限
- 最终审批由人工完成

### 6.2 生产发送门禁

普通审核卡片发送前必须同时满足：

1. 当前申请仍在 OA 待办中。
2. 附件发现、下载和解析数量闭环一致。
3. 不存在下载失败、解析异常或系统错误。
4. 必需检查项已完整执行。
5. 正式结论所需检查均为完成状态。
6. 决策稳定，发送熔断器未触发。
7. 幂等预占成功，避免重复通知。

证据不足时只输出明确标识的人工复核信息；系统异常时停止普通审核结论交付。

### 6.3 故障分级

| 状态 | 含义 | 处理方式 |
|---|---|---|
| `READY` | 数据和检查完整 | 允许进入正式卡片门禁 |
| `MATERIAL_MISSING` | 缺少必要材料 | 提示补充材料或人工确认 |
| `EVIDENCE_INSUFFICIENT` | 有材料但不足以证明结论 | 保持未决，不做确定性通过 |
| `OCR_LOW_CONFIDENCE` | OCR 或推断证据置信度不足 | 转人工复核 |
| `SYSTEM_ERROR` | 发现、下载、解析或依赖异常 | fail-closed，停止普通结论卡 |

## 7. 技术架构特点

### 7.1 规则与模型解耦

业务判断主要由本地确定性规则完成，模型负责解释与编排。规则可以独立测试、审计和修改，避免核心审批口径隐含在模型提示词中。

### 7.2 事实与结论解耦

文档解析先形成标准事实，再由规则消费。解析器升级不会直接改变规则结构，规则调整也不需要重写所有文档读取逻辑。

### 7.3 输出与执行解耦

飞书卡片只负责展示审核建议，OA 执行能力由独立安全开关控制。当前执行开关关闭，使"看得见建议"和"改变审批状态"保持清晰边界。

### 7.4 业务链路可观测

系统记录扫描、附件处理、规则判断、门禁状态、通知幂等和 OA 状态同步等阶段指标，可以按单据定位问题，而不依赖模型对话记录排障。

## 8. 当前建设成果

- OA 数据入口从不稳定的浏览器页面扫描迁移到 OA REST API
- 建立 PDF 文本、Vision OCR 和混合文档互补解析链路
- 建立合同、发票、账单、验收材料的结构化事实抽取
- 建立费用期间、主体、金额、币种等跨材料核验规则
- 建立字段级证据来源与置信度管理
- 建立附件发现、下载、解析的闭环指标
- 建立普通审核卡单一最终发送门禁
- 建立补证重试、超时 watchdog、幂等发送和熔断机制
- 建立真实案例回归与规则影子发布机制
- 保持 OA 自动操作、卡片动作和台账写入默认关闭

当前实时监听服务已运行，按固定周期发现目标 OA 待办并触发只读审核辅助链路。

## 9. 能力边界

为了保证结论可靠，系统明确保留以下边界：

- 材料缺失时不能推断为通过
- OCR 结果存在歧义时不能自动升级为确定事实
- 发票文件存在不等于已完成官方验真
- 表单金额一致不等于合同付款条件已满足
- OA 字段不能替代合同正文或发票原件中的必要证据
- 尚未支持的流程类型不会套用相近规则强行判断
- 模型生成的解释不能覆盖确定性规则和生产门禁
- 系统当前提供审批建议，不承担最终审批责任

## 10. 典型应用场景

### 10.1 合同付款审核

自动核对付款主体、收款单位、账户户名、合同主体、发票购销方、付款金额、付款阶段和费用期间，突出不一致项与缺失证据。

### 10.2 采购合同审核

自动抽取合同相对方、金额、币种、税务处理、付款条件、期限和责任条款，并与采购流程表单进行一致性核验。

### 10.3 发票与付款三方匹配

将 OA 申请、合同/订单和发票信息进行交叉匹配，识别金额、主体、币种、期间和验真状态风险。

### 10.4 材料完整性检查

识别合同、发票、采购申请、验收材料或账单是否缺失，并区分真实缺材料、证据不足、OCR 低置信度和系统处理异常。

1. 扩展更多高频财务流程。
2. 将更多历史审核经验沉淀为可维护规则和风险特征。

6. 完善知识库案例区，沉淀典型风险、规则说明和处理口径。

## 12. 汇报摘要

智能审批引擎不是一个"让模型决定是否审批"的系统，而是一套以业务证据和确定性规则为核心的审核辅助架构。

它通过 OA 数据连接、本地文档理解、跨材料事实核验、规则决策、智能解释和生产安全门禁，将原本依赖人工翻阅和经验判断的审核流程，转化为可追溯、可复核、可演进的数字化能力。

当前系统坚持只读建议和人工终审，在保证权限边界的同时，提升财务审批的信息获取效率、审核一致性和风险发现能力。
